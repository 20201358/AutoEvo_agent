# 技能管理器（双触发式）

本技能有两条触发路径，共用同一套执行工作流：

1. **用户主动触发**：用户直接下令管理技能。
2. **自主反思触发**：任务结束后由 `reflect` 节点调用，基于本次执行的证据生成建议，向用户提议。

## 核心原则

1. **任何改动前先告诉用户**：列出你要动哪些技能、为什么、具体怎么改；等用户说"执行"再动手。
2. **证据驱动**：每条提议必须引用本次任务的具体证据（某条命令失败、某个步骤返工、用户说了什么）。
3. **用户改目标就停**：如果用户说"算了，改做 X"，立即放弃当前技能操作，转去新任务。
4. **保守优先**：归档 > 删除；小步更新 > 大幅重写；不确定时询问而不是猜测。
5. **通用性优先**：技能的目标是"下次遇到类似任务能更快完成"，写技能时优先沉淀**流程**而不是**这一次的输出**。

## 触发路径 1：用户主动管理

| 用户说法 | 动作 | 工具 |
|---|---|---|
| "创建一个技能""保存成技能""记下来以后都这样" | 创建 | `create_skill` |
| "更新这个技能""把这条加进去" | 更新 | `update_skill` |
| "按 XX 要求改写""精简一下这个技能" | 精简/重写 | `refine_skill` |
| "合并这几个技能" | 合并 | `consolidate_skills` |
| "把这次对话变成技能" | 从历史提炼 | `create_skill_from_history` |
| "删掉这个技能" | 删除（先归档） | `delete_skill` |
| "清理技能库""精简技能库" | 审计+清理 | `audit_skills` → 选择性处理 |
| "看看有哪些技能""技能库现状" | 列出 | `list_skills` / `audit_skills` |

**即使用户主动下令，删除 / 合并 / 大幅精简（>30% 行数变化）仍需二次确认。**

## 触发路径 2：任务结束后自主反思

### 触发信号

| 信号 | 判断依据 | 建议动作 |
|---|---|---|
| 无对应技能，流程可复用 | 技能库无覆盖，任务可能重复出现 | 创建 |
| 有对应技能，但没能完成任务 | 技能步骤缺失 / 错误 / 过时 | 更新 |
| 有对应技能，但描述没匹配上 | 技能本可完成，但触发短语不全 | 更新描述 |
| 加载的技能过于啰嗦/冗长 | 步骤重复、与 skill_manager 重叠、引用过时 API | 精简 |
| 多个技能职责重叠 | 两个或多个技能都能覆盖同一流程 | 合并 |
| 有技能但用户明确说不要用 | 用户反馈"别用那个流程" | 更新或删除 |
| 任务反复执行才成功 | 中间有重试、绕路，说明步骤不清晰 | 更新 |
| 任务在未完成状态下结束 | 被中止 / 达到迭代上限，且原因是技能缺陷 | 更新 |
| 技能体量过大且部分段落从未被引用 | 正文 > 200 行、含从未被加载的子流程 | 精简 |
| 任务成功且技能完美覆盖 | 技能正确加载并完成任务 | **不提议** |
| 任务是一次性琐事 | 无复用价值 | **不提议** |

### 反思流程

**第一步：收集信号**

- 用户反馈：满意 / 不满 / 未表态
- 执行结果：成功 / 反复才成功 / 部分成功 / 未完成即结束
- 技能使用：是否加载了技能、是否帮上忙、是否有缺失
- 技能库问题（用 `audit_skills` 查）：重复、冗余、过时、矛盾、体量异常

**第二步：对照技能库生成建议**

用 `audit_skills` 拿硬指标（行数 / 载入次数 / 与其他技能的相似度），再结合本次任务的具体行为，生成结构化建议。

判断时**必须引用本次任务中的具体证据**，不能凭空猜测。

**第三步：排序与去冲突**

- 优先级：失败/用户不满 > 反复才成功 > 未完成即结束 > 合并 > 精简 > 清理 > 创建
- 最多保留 5 条，超出时合并同类项或省略低优先级
- 冲突检查：
  - 同一技能不能同时被建议"更新"和"删除"
  - 被合并的技能不能再单独被"清理"
  - 被删除的技能不能再被建议"更新"
- 有冲突时只保留优先级高的那条

**第四步：向用户提议（支持多条）**

```
【技能管理建议】
本次任务后发现 N 条可管理的技能项：

1. 建议动作：创建 / 更新 / 精简 / 合并 / 删除 / 清理
   涉及技能：<技能名1>, <技能名2>, ...
   保留技能：<技能名>              （仅合并时填写）
   归档技能：<技能名1>, <技能名2>   （仅合并/清理/删除时填写）
   原因：<引用本次任务中的具体证据>
   具体改动：<要做什么>
   危险度：低 / 中 / 高             （删除、大幅精简、合并 → 高）

2. ...
```

**第五步：按用户回应执行**

- "全部执行" → 按顺序执行，每条执行前展示具体改动
- "只执行第 N 条" → 只执行指定编号
- "改一下方案" → 根据用户反馈重新生成提议
- "跳过全部" → 放弃本次提议
- 未明确表态 → 不执行任何操作
- **用户说别的任务** → 立即放弃技能操作，转去新任务，不要再提

## 执行工作流

### A. 创建

1. `list_skills` 查重
2. 选名称（snake_case，动词开头，如 `deploy_docker`、`extract_docx_tables`）
3. 写描述（**必须含具体触发短语**，否则以后匹配不上）
4. 写正文（何时使用、工作流、示例、边界情况）
5. `create_skill(name, description, body)`
6. `read_skill(name)` 读回验证

### B. 更新

1. `read_skill(name)` 读取
2. 确定改动类型：新增步骤 / 修正错误 / 重写描述 / 补充示例
3. 保留 name 不变，`update_skill(name, description, body)`
4. 读回验证

### C. 精简 / 按要求改写（refine）

适用：用户说"精简 / 优化 / 重写 / 按这个要求改"。

1. `read_skill(name)` 看现状
2. 起草改写指令（一句话说清要改什么、保留什么）
3. **把指令与预估变化告诉用户**（例："把 X 技能从 240 行精简到 ~120 行，删除与其他技能重叠的段落"）
4. 用户同意后调用 `refine_skill(name, instructions)`
5. `read_skill` 验证；行数下降 > 30% 时再次提示用户确认结果

### D. 合并（consolidate）

适用：多个技能职责重叠，或用户要求"合并成一个"。

1. 识别候选（用 `audit_skills` 的相似度指标 + 自己读内容判断）
2. 向用户提议并等待确认，说明：
   - 新技能名与描述（触发短语怎么合并）
   - 哪些旧技能会被归档
   - 大致会保留哪些段落、删掉哪些
3. 用户同意后调用 `consolidate_skills(source_names, new_name, new_description)`
4. `read_skill(new_name)` 验证
5. 旧的自动归档到 `.archive/`（可恢复）

### E. 从历史会话提炼

适用：用户说"把这次对话变成技能""以后遇到这种任务都这样做"。

1. 拿到当前 conversation_id
2. 问用户技能名与侧重点（可选）
3. `create_skill_from_history(conversation_id, skill_name, hint)`
4. `read_skill(skill_name)` 验证，向用户展示提炼结果

### F. 删除

1. 与用户确认
2. `search_skills` 检查是否有其他技能引用它
3. `delete_skill(name, archive=true)` —— **默认归档而非物理删除**
4. `list_skills()` 验证

### G. 清理（精简技能库）

适用：用户说"技能库太乱了""精简一下技能库"。

1. `audit_skills` 拿硬指标
2. 标记候选（长期未用、内容矛盾、职责被完全覆盖、描述模糊、正文为空）
3. 生成清理报告（哪些建议归档、哪些建议合并、哪些保留），**向用户确认**
4. 分批执行（每批 ≤ 5 个），批间汇报

## 日志格式

每次操作打印一行摘要：

- `[SKILL] created: <name>`
- `[SKILL] updated: <name>`
- `[SKILL] refined: <name> (<old>→<new> 行)`
- `[SKILL] merged: <被合并> into <保留>`
- `[SKILL] created-from-history: <name>`
- `[SKILL] archived: <name>`
- `[SKILL] pruned: <name> (reason: ...)`

## 安全规则

- 绝不删除或修改 `skill_manager` 本身
- 删除、合并、大幅精简必须先确认
- 优先归档而非物理删除
- 创建前必须查重，避免与现有技能重复
- 合并时必须保留原技能的所有触发短语
- 提议必须引用具体证据
- 用户拒绝后不重复推销同一件事，除非出现新证据
- 正文超过 500 行时拆分到 `references/`
- 任务成功且技能完美覆盖时**保持沉默**，不要为了显得主动而制造无意义提议
- **用户中途改目标**：立即停止技能操作，转去执行新任务，不要再纠缠

## 工具依赖

| 工具 | 用途 |
|---|---|
| `list_skills()` | 列出所有技能的名称与描述 |
| `read_skill(name)` | 读取技能完整内容 |
| `search_skills(query)` | 按关键词检索技能 |
| `audit_skills()` | 技能库审计（行数/载入次数/相似度） |
| `create_skill(name, description, body)` | 创建技能 |
| `update_skill(name, description, body)` | 更新技能 |
| `refine_skill(name, instructions)` | 按指令精简/重写技能（LLM 辅助） |
| `consolidate_skills(sources, new_name)` | 合并多个技能（LLM 辅助） |
| `create_skill_from_history(conv_id, name)` | 从历史会话提炼技能（LLM 辅助） |
| `delete_skill(name, archive)` | 归档 / 删除技能 |
| `restore_skill(archived_name)` | 恢复被归档的技能 |
| `read_file` / `write_file` | 需要处理 references/ 时使用 |

## 边界情况

- **用户主动下令但操作有风险**：仍要确认，尤其是删除和合并
- **用户没表态**：不要强行提议
- **一次发现太多问题**：最多呈现 5 条，按优先级排序
- **建议之间冲突**：先让用户二选一，不能两条都执行
- **提议被拒绝**：同一件事不再重复提
- **名称重复**：创建前查重，同名时询问是更新还是换名
- **frontmatter 非法**：报告错误，不要猜测
- **技能过大**：正文超 500 行拆分到 `references/`
- **循环引用**：不要在另一个技能里引用 `skill_manager`
- **LLM 合并/精简失败**：报告错误，不要留半成品；归档动作只在合并成功后触发
- **用户说"别问了直接做"**：也至少在执行前用一句话播报要做什么，免得用户不知道
